# 1.4 操作系统结构

## 1. 内核与非内核部分

操作系统可以分为**内核部分和非内核部分**。内核是操作系统最基本、最核心的部分，运行在内核态。

按本节的学习框架，操作系统的核心功能可以分为两组：

| 功能组 | 主要内容 |
| ------ | -------- |
| 基本功能 | 时钟管理、中断处理、原语等 |
| 系统资源管理功能 | 进程管理、存储器管理、设备管理等 |

**原语是具有原子性的操作。** 教材中常表述为“一旦开始执行，就必须连续执行完毕，不可被中断”。重点是相关操作作为一个不可分割的整体完成，不能让其他并发执行者观察到或破坏中间状态。

> “不可被中断”是对原子性的简化理解；具体实现可以使用原子指令、适当的互斥或中断控制等机制，不能理解为所有原语都能仅靠关闭中断实现多核同步。

## 2. 大内核（宏内核／单内核）

**大内核将基本功能和主要的系统资源管理功能都放在内核中，在内核态运行。**

例如，进程管理、存储器管理、设备管理等模块都在内核中，可以直接相互调用。

- **优点**：内核中的各模块协作方便，通信和状态切换开销较小，通常有较好的性能。
- **缺点**：内核庞大、功能繁杂，模块之间联系紧密，难以维护；某个内核模块出错，可能导致整个系统崩溃。
- **典型例子**：Linux、传统 UNIX。

## 3. 微内核

**微内核只在内核中保留最必要的功能，把较多的系统服务移到用户态，以独立服务进程的形式运行。**

可以先按“保留基本功能，把较多资源管理服务移出内核”来记忆，但不能理解成微内核完全不管理资源。微内核通常仍需提供基本调度、进程间通信和底层地址空间管理等必要机制，具体边界取决于实现。

**移出内核的系统服务仍属于操作系统，只是不在内核态运行。** 应用程序请求这些服务时，通常需要通过微内核与相应的服务进程通信。

- **优点**：内核较小，服务相对独立，便于扩展、维护和故障隔离。
- **缺点**：服务之间往往需要多次进程间通信，可能增加用户态与内核态切换、进程或线程切换的开销。

独立用户态服务进程之间，不能像同一内核中的模块一样直接进行普通函数调用。教材通常按**通过内核的消息传递间接通信**来理解；实际系统也可能支持共享内存等通信方式。

**用户态服务模块出错，通常可以被隔离，不会像内核模块出错那样直接破坏整个内核。** 但关键服务故障仍可能使系统无法正常提供服务，因此不能绝对理解成“内核外模块出错一定不会影响整个系统”。

### Windows NT 的分类

一些教材将 **Windows NT** 列为采用微内核思想的操作系统，可按课程口径记忆。严格讨论实际结构时，它通常被归为**混合内核**，不宜直接等同于纯微内核：它具有较小的核心层，但许多高层服务仍在内核态执行。参见微软的 [One Windows Kernel](https://techcommunity.microsoft.com/blog/windowsosplatform/one-windows-kernel/267142)。

## 4. 为什么微内核的状态切换可能更多？

假设应用程序请求的一项服务，同时涉及进程管理、存储器管理和设备管理。

### 大内核中的处理

**应用程序（用户态）→ 内核中的多个管理模块协作（内核态）→ 应用程序（用户态）。**

进入内核后，各管理模块之间可以直接调用，**不必为了每调用一个模块就切回用户态**。

在不考虑阻塞、抢占等情况的简化模型中，整个请求可以只有进入内核、返回用户态这两次状态切换。

### 微内核中的处理

**应用程序（用户态）→ 微内核（内核态）→ 服务进程（用户态）→ 微内核（内核态）→ 另一个服务进程（用户态）……**

当多个用户态服务进程需要协作时，通常要通过微内核传递消息，因而可能发生更多的状态切换和执行上下文切换。

**状态切换有成本。** CPU 需要保存、恢复必要状态，跨进程通信还可能涉及调度和地址空间切换等工作。频繁切换会增加开销，影响系统性能。

> 这里的“变态”规范写作**处理机状态切换，即用户态与内核态切换**。它与进程切换不是同一个概念：进入内核态时，不一定换了一个进程。实际切换次数取决于服务流程和实现，不能只凭内核类型确定固定次数。

## 5. 对比记忆

| 对比项 | 大内核 | 微内核 |
| ------ | ------ | ------ |
| 内核包含的功能 | 基本功能及主要资源管理功能 | 最必要的基本机制 |
| 较多系统服务的位置 | 内核态 | 用户态服务进程 |
| 模块协作方式 | 内核内直接调用 | 常通过进程间通信协作 |
| 切换与通信开销 | 通常较小 | 通常较大 |
| 扩展、维护与故障隔离 | 相对较难 | 相对较方便 |

**记忆：大内核功能集中，协作开销小；微内核功能精简，服务隔离好。**

## 6. 分层结构

**将操作系统划分为若干层，各层通过明确的接口使用下层提供的服务。** 最底层是硬件，最高层是用户接口；内核内部也可以按层次组织。

本节按**严格分层模型**记忆：每层只能单向调用**相邻低层**提供的接口，不能跨层调用。更一般的分层设计也可能允许调用非相邻的低层。

**调用方向：用户接口 → 上层功能 → …… → 底层功能 → 硬件。**

### 优点

- **便于调试和验证**：自底向上逐层调试；底层验证通过后，再验证依赖它的上层。
- **易于扩展和维护**：各层之间的接口清晰、固定；保持接口不变时，可以修改某一层的内部实现，减少对其他层的影响。

### 缺点

- **难以合理定义各层边界**：不同功能之间的依赖关系复杂，不容易安排成严格的上下层关系。
- **效率较低**：严格分层不允许跨层调用，一次系统调用可能需要经过多层接口，增加执行时间。

## 7. 模块化结构

**将内核划分为多个模块，各模块通过约定的接口相互协作。**

对于支持可加载内核模块的设计，可以概括为：

**内核 = 主模块 + 可加载内核模块。**

| 组成 | 作用 | 例子 |
| ---- | ---- | ---- |
| 主模块 | 提供内核必需的核心功能 | 进程调度、核心内存管理等 |
| 可加载内核模块 | 按需要动态加载到内核，扩展功能 | 设备驱动程序模块等 |

**添加新模块通常无需重新编译整个内核**，但新模块本身仍需要编译，并与目标内核接口兼容。模块加载后在内核态运行。

### 优点

- **模块之间逻辑清晰，易于维护**：每个模块承担相对独立的功能。
- **便于并行开发**：确定模块间接口后，可以由不同开发者同时开发多个模块。
- **增强操作系统的适应性**：支持动态加载新模块，按需要扩展功能。
- **效率较高**：不受严格分层中“只能调用相邻低层”的限制，模块可通过接口直接调用其他模块，无需为了模块间调用而采用跨进程消息传递。

> “可直接调用其他模块”不等于可以任意访问其内部实现，仍需遵守接口和依赖关系。例如，Linux 可加载模块通过导出的符号使用内核及其他模块提供的功能，参见 [Linux 内核符号说明](https://www.kernel.org/doc./htmldocs/kernel-hacking/symbols.html)。

### 缺点

- **接口设计困难**：模块间接口未必一开始就定义得合理、实用。
- **模块之间存在相互依赖**：难以像严格分层那样自底向上逐层验证，整体调试和验证较复杂。

**模块化与宏内核并不矛盾。** 模块化关注代码和功能如何组织，宏内核关注哪些功能运行在内核态；Linux 就采用了支持可加载模块的宏内核设计。

## 8. 外核（Exokernel）

**外核的核心思想：将资源保护与资源管理策略分离。** 外核负责安全地分配、复用和保护底层硬件资源，将较多管理策略与高层抽象交给用户态的库操作系统或应用程序。参见 [MIT 外核项目说明](https://pdos.csail.mit.edu/archive/exo/)。

### 功能分工

| 部分 | 主要职责 |
| ---- | -------- |
| 外核 | 分配和回收底层资源，检查访问权限，保证不同应用使用资源时的安全与隔离 |
| 用户态库操作系统／应用程序 | 根据需求实现资源管理策略和高层抽象，如文件系统、内存管理策略等 |

外核向上暴露较接近硬件的资源，如物理内存页、磁盘块、CPU 时间片等，避免强制所有应用采用同一套高层抽象。

> 不宜简单记成“普通内核负责调度、通信，再外挂一个外核”。外核本身就是一种内核设计：仍需提供安全复用 CPU 等资源的必要机制，但将较多策略交给用户态。

### 优点

- **资源使用更灵活**：可向用户程序提供较少抽象的硬件资源，由应用或库操作系统选择适合自己的管理方式。
- **有助于提高效率**：减少不必要的统一抽象与转换开销，便于针对应用优化。

### 缺点

- **降低系统接口和管理方式的一致性**：不同应用可能采用不同的库操作系统、抽象和策略。
- **增加系统设计与应用开发的复杂性**：更多资源管理工作交给用户态，需要处理兼容、协作等问题。

> “不虚拟、不抽象”是强调尽量暴露底层资源，并不意味着完全没有接口、地址映射或安全检查，也不意味着应用可以任意访问硬件。

## 9. 各种结构的速记对比

| 结构 | 核心特点 | 主要优点 | 主要缺点 |
| ---- | -------- | -------- | -------- |
| 分层结构 | 按层次通过下层接口调用 | 易于逐层调试、验证和维护 | 层次边界难划分，多层调用有开销 |
| 模块化 | 按功能划分模块，通过接口协作 | 便于并行开发和扩展，直接调用效率高 | 接口设计难，依赖关系使验证复杂 |
| 宏内核 | 主要功能集中在内核态 | 内部直接调用，性能通常较高 | 内核庞大，模块故障可能导致系统崩溃 |
| 微内核 | 最小必要机制留在内核，较多服务放到用户态 | 易维护，故障隔离较好 | 跨进程通信和状态切换开销较大 |
| 外核 | 内核保护底层资源，用户态决定较多管理策略 | 灵活，可减少不必要的抽象开销 | 一致性较弱，设计与使用更复杂 |
